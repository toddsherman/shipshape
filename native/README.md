# Shipshape for macOS — 0.3.17 preview

A native SwiftUI app for macOS 13 or later, in the menu bar and the Dock, built for Apple silicon and Intel. It watches the developer stack people install to build apps with AI coding tools such as Claude Code and Codex, and shows the easiest way to install each fix. No Python, Node, Homebrew, account or API key is needed to run it.

## Install and use

Copy **Shipshape.app** from the disk image into Applications and open it. Add the folders that hold your projects, run the first check, then enable notifications. Optionally turn on **Start Shipshape when I log in** in Settings. Each Mac builds its own inventory.

Release builds are Developer ID signed and notarized by Apple, with tickets stapled to the disk image and the app. Each release on GitHub includes `SHA256SUMS.txt` with the disk image's checksum. Never disable Gatekeeper to install or distribute a build.

From 0.3.14, Shipshape updates itself with [Sparkle](https://sparkle-project.org). Once a day it reads `appcast.xml` from the latest GitHub release (**Check for Updates…** in the app menu and Settings checks right away). A newer version is shown with its release notes, and nothing is installed until you click **Install Update**. Sparkle then downloads the disk image, verifies its EdDSA signature against the public key in `Info.plist` and its Developer ID signature against the installed copy's, and quits, replaces and reopens Shipshape. The feed itself is signed too, so its notes and links can't be altered. **Check for updates automatically** in Settings turns off the daily check; updates are never installed without the click.

A fresh check runs every time the app opens, including at login, once the network is up (after 30 seconds it checks anyway). Checks also run daily at 9 a.m. America/Los_Angeles while the app is open, and catch up after waking. **Check now** runs one whenever you like; the dashboard footer and menu show the last check's time and how long ago it was ("10:36 AM (5 minutes ago)"). There is no background polling between checks. A first check takes a few minutes because NVD limits requests without an API key; NVD results are reused for 20 hours. Quitting the app stops monitoring.

The **Security** page starts with a summary card: how many items need attention, a ring with the share of inventory items that need no action (no findings, or only findings waiting for a fixed release), and a bar of every item by its most urgent finding. Six tiles sort findings into malicious packages, known exploitation, security fixes, end of support, waiting for a fix and updates; malicious packages and known exploitation are red when present. A tile lists only its findings, and **Needs attention**, the default list, holds the first four kinds. The menu bar panel shows the same kinds with their counts, and clicking one opens the Security page at that list.

**History** logs every recommendation: when it was first found and, once a check no longer reports it, when it was resolved and how. "Updated to 9.0.2" means the same software is now at another version; "Removed" means an older Homebrew copy was cleaned up; "Removed from this Mac" or "from the project" means the software is gone; "Project folder no longer checked" means its folder was taken out of Settings; and "No longer reported" means the software is unchanged but the advisory no longer matches. A finding that comes back, or is still reported after a version change, starts a new entry. Findings kept as unverified after a failed check stay open. History is stored with the latest result in Application Support, keeps the newest 10,000 entries (dropping the oldest resolved ones first), and exports as CSV. The first launch of a version with History starts it from the last saved result.

Notifications are deduplicated by installation, version, fix version, advisory identifiers and known-exploitation status. Malicious packages get their own alert title. A bundled Sparkle whose app has a new release gets an alert naming the app, which says only that the release may include a newer Sparkle. Failed source checks produce a separate alert and keep earlier findings visible as unverified.

## What it checks

| --- | --- | --- |
| Project dependencies | package-lock.json, pnpm-lock.yaml, yarn.lock, bun.lock, uv.lock, poetry.lock, pinned requirements.txt, Cargo.lock, Gemfile.lock, go.mod, Package.resolved (Swift, including inside Xcode projects), composer.lock, pubspec.lock, packages.lock.json (.NET), mix.lock (Hex packages) and gradle.lockfile in chosen folders, up to five levels deep | OSV (npm, PyPI, crates.io, Go, RubyGems, Swift, Packagist, Pub, NuGet, Hex, Maven), including OpenSSF malicious-package reports |
| GitHub Actions | `uses:` lines in each project's `.github/workflows` | OSV's GitHub Actions advisories, with version ranges compared by Shipshape: exact versions directly, moving tags such as `@v4` as the newest release in that major version, and commit pins by the version comment beside them. Branches and bare commits are listed as not checkable |
| Editor extensions | VS Code, VS Code Insiders, Cursor, Windsurf and VSCodium extension folders | Microsoft's [list of extensions removed from the Visual Studio Marketplace](https://github.com/microsoft/vsmarketplace/blob/main/RemovedPackages.md), for those removed as malware, impersonation or untrustworthy. Cursor, Windsurf and VSCodium install from Open VSX, where an identifier may belong to another publisher, so their findings say so |
| Global packages | npm (Homebrew, standard, nvm, fnm), Bun and pnpm globals, python.org/Homebrew/uv/pyenv site-packages, pipx and uv tools, `cargo install` crates, `go install` programs (their module and the modules built into them, read with `go version -m`), Ruby gems in Homebrew, rbenv, mise and per-user Rubies (the newest copy of each, which is the one Ruby loads; older copies and default gems a newer install replaced are skipped), the npx cache | OSV |
| MCP servers | Claude Code, Claude, Codex, Cursor, Windsurf, VS Code and Gemini CLI settings, plus project `.mcp.json` | OSV for pinned servers and npx-cached versions |
| AI coding tools | Claude Code (native, local or cask), Codex CLI, Gemini CLI, GitHub Copilot CLI (cask or native), OpenCode (Homebrew, desktop or native); Claude, Codex, ChatGPT, Cursor, Windsurf, VS Code, Zed, Ollama and LM Studio apps | OSV for the Claude Code, Codex, Gemini and Copilot npm packages; OpenCode's own GitHub advisories; NVD where a CPE exists |
| Runtimes | Node (standard, Homebrew, nvm, Volta, fnm), Bun, Deno, uv, Go (go.dev or Homebrew), python.org, Homebrew, uv and pyenv Pythons; Node, Python, Go, Ruby, Bun and Deno installed with mise; Rust, Ruby, PHP and OpenJDK from Homebrew | Vendor rules for Node and Bun; OSV for Go's standard library and uv; NVD for the rest. A Python's fix is the release in its own branch when NVD lists one (3.12.14 for 3.12.13), and a uv Python is upgraded within its branch with `uv python upgrade`. uv keeps the old patch release after an upgrade; it's listed as an older copy to remove, and only the newest patch of each branch is checked |
| Homebrew | Every installed formula and cask, including retained older copies | Vendor rules for PostgreSQL (including the libpq client library) and OpenSSL; OSV for Docker Compose's Go module; NVD for catalog tools and libraries (curl, git, sqlite, libxml2, libpng and others) |
| Developer apps | Catalog apps in /Applications and ~/Applications: browsers, terminals, Docker, JetBrains IDEs, Postman, Tailscale and others | NVD where a CPE exists |
| Self-updating apps (Sparkle) | Any non-App Store app in /Applications or ~/Applications with an https Sparkle feed (`SUFeedURL`) or a bundled `Sparkle.framework`, on the catalog or not | The app's own feed for newer releases, compared by build number as Sparkle does (beta channels, other platforms and releases needing a newer macOS are skipped). The bundled Sparkle version is checked against Sparkle's advisories in OSV; the fix is updating the app. When the app is already at its newest release (by its own feed or Homebrew's cask data), there is nothing to install: the finding waits in **No fix released yet**, with no button and not counted as needing attention, and Shipshape alerts you when a newer release appears. Until then it keeps waiting, even when the app's feed can't be read. Apps that set their feed in code rather than in `SUFeedURL`, such as Codex, are covered when the catalog lists their public feed; for any other app Shipshape can't show is current, the card keeps its button and says Shipshape can't tell whether a newer release is out. The alert names the app and says the release may include a newer Sparkle, since that isn't known until it's installed and checked. Apps that ship their own modified Sparkle (a version like `1.22.0 1354-g4e0506a`) are noted, since the version may not show fixes made since |
| Apple | Software Update, including Command Line Tools | Update eligibility only |

**Excluded by design:** Google Chrome, whether installed directly or with Homebrew, and every app installed from the Mac App Store. They update through Chrome's own updater and the App Store, and are skipped entirely: not listed, checked or counted as findings.

Versions are read by their first number, so an app that reports `Build 4215` compares as 4215. As a final check on every scan, an update is never offered when its version is the installed release written differently. Homebrew rebuilds such as 15.0.0 → 15.0.0_1 still count, and anything skipped is noted under Coverage.

CISA's Known Exploited Vulnerabilities catalog raises the priority of any finding whose CVE is listed. Homebrew's public metadata marks ordinary newer releases as updates, not security fixes. RustSec "unmaintained" notices are not reported as vulnerabilities.

NVD matching uses only explicit version ranges or exact versions on macOS-applicable configurations. Pre-release and unbounded "all versions" entries are ignored. NVD can lag vendor advisories, and Homebrew sometimes ships patches without changing a version, so NVD findings say so.

**No fix released yet.** Sometimes NVD lists no fixed version and the installed Homebrew copy is already Homebrew's newest release, so updating can't help. Those findings appear in their own group with no update command, and they don't count toward items needing attention or trigger alerts. They show the fix version when an advisory's text names one ("before 1.22.3"). When Homebrew ships a newer release, the finding becomes an ordinary one with its command, and the alert says **Fix now available**. If Homebrew's data can't be loaded, the finding keeps waiting.

Vendor rules fail closed: a missing page or an unfamiliar format marks the check as failed instead of reporting software as safe. The one exception is a new OpenSSL release branch with no vulnerability page yet. It counts as having no published vulnerabilities, but only when OpenSSL's vulnerabilities index loads, links other branches and doesn't list that one.

To cover more software, add an entry to `native/Sources/Catalog.swift` with its bundle IDs, Homebrew formulae or casks, and one advisory source: an NVD CPE (`vendor:product`), an OSV package (`{major}` in a name follows the installed major version, as in Go's `/v5` module paths), or the project's GitHub repository advisories. Check that the source has data before adding it; the app reports nothing for a CPE or package it doesn't know, and a product whose versions don't match its package's versions needs its repository advisories instead. A Sparkle app that sets its update feed in code rather than in `SUFeedURL` can list its public appcast as `feed`.

**Coverage is partial.** Vulnerabilities in editor extensions (no public database covers them), CocoaPods, container images, unpinned MCP servers that npx hasn't cached, GitHub Actions pinned to branches or bare commits, software outside the catalog and arbitrary install paths aren't checked. A newer version alone is not a vulnerability. This is an update monitor, not a malware scanner or an assurance that a Mac is secure.

## Installing updates

Each finding lists the ways to install its fix, best first, with the others under **Other ways to update**. The app checks how the software was installed and what this Mac has (Homebrew, mise, npm, pnpm, Yarn, Bun, corepack, uv, Poetry, Cargo, Bundler, Go, nvm, Volta, fnm), and uses Homebrew's data on whether each app updates itself. Options come in four kinds:

- **Terminal command**, matched to the install method: `brew upgrade curl`, `cd ~/Projects/app && npm install next@16.4.1`, `npm audit fix` for transitive dependencies, `uv lock --upgrade-package`, `mise upgrade node`, `claude update`, `opencode upgrade` or the owning interpreter's `pip`. **Copy**, to the right of the command, puts it on the clipboard to paste into any terminal.
- **Website**: the vendor's download page, nodejs.org, python.org or go.dev. Only https pages are offered.
- **App**: opens an app that updates itself so its updater can install the release.
- **File**: opens requirements.txt, package.json or an MCP configuration where a pin has to change, in your text editor (never the app the file type would launch), and only when it's a plain, non-executable text file inside a chosen project folder or one of the MCP settings files Shipshape reads.

For a directly downloaded app, one that updates itself leads with opening it, then a Homebrew command if Homebrew is installed, then the download page. An app without a self-updater leads with Homebrew or the download page. Homebrew apps that update themselves get `--greedy` so Homebrew includes them. When a project's package manager isn't installed, the command first installs it (`corepack enable pnpm`, `npm install -g yarn`, `brew install uv`), or the first option is its install page. Older Homebrew copies get `brew upgrade X && brew cleanup X`, because Homebrew deletes them only once its newest build is installed; removing just that copy from Homebrew's Cellar is offered as an alternative. Pinned formulae are unpinned before upgrading, and a pinned formula's old copy is removed without upgrading. Homebrew rebuilds, such as 26.12.1 → 26.12.1_1, appear as updates. Apple updates open Software Update. Installers downloaded from nodejs.org or python.org are checked with Apple's notarization assessment before `sudo installer` runs. 

**Commands only for what your account can change.** Before offering a command, Shipshape checks that the signed-in account can write where it acts: the project folder, its lockfile, `node_modules` (including npm's `@scope` folders) and `.venv`, Homebrew's Cellar and Caskroom, the global package folder or Python `site-packages`, the npx cache and MCP settings files. If not, the finding stays listed (the vulnerable code is still on the Mac) with a lock notice in place of the command, naming the folder and its owner. Another account's projects say to make the fix from that account. Homebrew installed by another account says only that account can upgrade it, also noted under Coverage. A root-owned folder in a project is usually left by an install run with `sudo`; change its owner back to your account. Shipshape never suggests running package managers with `sudo`. Adding a project folder that belongs to another account, or that includes system or Homebrew folders, shows a warning in Settings.

Project scans skip app bundles, Homebrew's own folders (`/opt/homebrew`), `/usr`, `/System`, `/Library`, `~/Library` and Go's module cache, so a project folder set high up, even `/`, doesn't pick up package-manager internals as projects. A folder chosen inside one of those is still checked.

Findings whose recommended command is the same, or differs only in what it acts on, appear as one card with one combined command (`brew upgrade a b c`, `rm -rf dir1 dir2`, `npm install next@16.4.1 ai@5.0.52`), followed by each finding's version, reason, location, advisories and any alternatives of its own. All older Homebrew copies share one card, and so do a project's indirect dependencies under its `npm audit fix`. **All commands…** on the Security page lists every recommended Terminal command in the list showing, combined the same way, with each project's commands kept together, to review and copy one at a time or all at once. Commands that can't take several targets, such as `cargo update --precise`, stay one per line. On the developer's Mac, 187 security findings became 44 cards and 28 commands, and 52 updates became 4 cards and 3 commands.

Package names and versions are checked against each ecosystem's naming rules and shell-quoted before they appear in a command, and nothing is ever run by the app. Review a command before running it; dependency updates can change behavior.

## Hardening

- **Untrusted project files.** Project scans don't follow links, read only regular files up to 64 MB, and stop after 60 seconds, reporting what was left. Parsers are linear in file size; a `requirements.txt` crafted to slow a regular expression parses 20,000 lines in milliseconds.
- **No hidden characters in commands.** A path or name containing control, formatting (including bidi) or line-separator characters gets no Terminal command. Pasted into a shell, such characters could erase the line or run something else. The finding shows where they are instead.
- **Opening files and apps.** Files open only in your text editor, and only when they are plain, non-executable text files inside a chosen project folder or one of the known MCP settings files. A repo can't turn "Open package.json" into running a script. Apps open only from Applications folders.
- **No Homebrew code runs.** The Homebrew inventory is read from `Cellar`, `Caskroom`, `opt` and `var/homebrew/pinned` directly. Other programs (`node --version` and similar, `softwareupdate`) run only if this account or root owns them and no one else can change them, with a minimal environment.
- **Bounded downloads.** Every source has a size limit, enforced while downloading: a larger declared size is refused before the body arrives, and transfers stop as soon as they pass the limit.
- **Signed updates only.** Shipshape installs an update only when the release's disk image carries both an EdDSA signature from the update key and the same Developer ID, and the feed describing it is signed with the same key. A tampered feed is refused with an error. Sparkle's XPC services, which only sandboxed apps use, are removed from the bundle.
- **Quoted names and no stray keys.** Package names are quoted in every command, even after validation. An MCP server's arguments are recorded only when every option before the package is known, so an option's value, such as an API key, is never mistaken for a package name.

## Data and privacy

State lives in `~/Library/Application Support/Shipshape/state.json` (folder 0700, file 0600). It contains local paths, project folders, package names, versions, results and notification fingerprints. There is no analytics, account, remote inventory or AI service.

Package names and versions are sent to OSV, product names and versions to NVD, and release and advisory lookups to Homebrew, GitHub, Node, PostgreSQL and OpenSSL. Self-updating apps' Sparkle feeds are fetched from each app's developer, the same request the app makes when it checks for updates. Shipshape's own update check fetches its feed and, when you install, the disk image from GitHub; the request names Shipshape's and Sparkle's versions, and Sparkle's system profiling is off. **Private package names in your lockfiles are included in OSV queries.** MCP settings are read for each server's command and arguments only; environment variables, headers and keys are never kept. Lockfiles are read as text and nothing in a project is run. Exported reports contain local paths and package names, so review them before sharing.

To uninstall, turn off Start at login, quit the app and move it to Trash. Remove the Application Support folder separately if you no longer need saved results.

## Development

Requires Xcode or a matching Swift compiler and macOS SDK. The one third-party package is Sparkle, for Shipshape's own updates: `native/sparkle.sh` downloads its pinned release into `native/work`, checks the SHA-256, and the build embeds and signs it.

```sh
bash native/test.sh
SIGN_IDENTITY="Developer ID Application: YOUR NAME (TEAMID)" bash native/build.sh
SIGN_IDENTITY="Developer ID Application: YOUR NAME (TEAMID)" bash native/package.sh
bash native/notarize.sh security-monitor-notary
bash native/appcast.sh
```

To try a development build without touching the installed app's saved results, launch it with `SHIPSHAPE_STATE_DIR` set to another folder, for example `open -n --env SHIPSHAPE_STATE_DIR=/tmp/shipshape-state dist/Shipshape.app`. Without it, a development build uses and changes the installed app's data. The name and version come from `native/Resources/Info.plist`; the build, packaging and notarization scripts read them from there, and `appName` in `Feeds.swift` is the name shown in the app. The notary keychain profile keeps its original name. Without `SIGN_IDENTITY`, the build uses an ad-hoc signature for local development only. Tests cover version ordering, vendor range rules, each lockfile format, MCP command parsing, OSV alias handling and fix selection, NVD range and platform evaluation, command quoting and routing, failed-check retention, notification fingerprints and Pacific-time scheduling.

For a command-line scan with the same engine (pass an output file and any project folders):

```sh
xcrun swiftc -swift-version 5 -O -parse-as-library native/Sources/{Models,Catalog,Lockfiles,Inventory,Advisories,Commands,Feeds}.swift native/Tests/Check.swift -o native/work/check
native/work/check native/work/live-scan.json ~/Projects
```

Every rebuilt DMG needs its own notarization before sharing. `native/notarize.sh` submits the DMG with a saved notarytool keychain profile, waits for **Accepted**, staples the DMG and app, verifies Gatekeeper acceptance and rewrites the checksum. Run `native/setup-notarization.command` once in Terminal to save the `security-monitor-notary` profile. Never put Apple passwords in source files or shell history.

Updates are signed with an EdDSA key. Run `native/setup-update-key.command` once in Terminal: it creates the key in your login Keychain (account `shipshape`), or reuses it, puts the public half in `Info.plist` as `SUPublicEDKey`, and offers to write a backup to put in your password manager. **Keep that backup.** Installed copies trust only this key, so losing it means everyone has to download the next release by hand. A signed release build refuses to start without `SUPublicEDKey`. After notarizing, `native/appcast.sh` writes `dist/appcast.xml` for the disk image, with its signature and the version's dated `CHANGELOG.md` section as release notes, then signs the feed. Attach `appcast.xml` to the GitHub release with the disk image and `SHA256SUMS.txt`; installed copies read it from the latest release's download link. Development builds launched with `SHIPSHAPE_STATE_DIR` don't check for updates unless `SHIPSHAPE_CHECK_UPDATES=1` is also set.
