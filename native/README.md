# Shipshape for macOS — 0.3.32 preview

A native SwiftUI app for macOS 13 or later, in the menu bar and the Dock, built for Apple silicon and Intel. It watches the developer stack people install to build apps with AI coding tools such as Claude Code and Codex, and shows the easiest way to install each fix. No Python, Node, Homebrew, account or API key is needed to run it.

## Install and use

Copy **Shipshape.app** from the disk image into Applications and open it. Add the folders that hold your projects, run the first check, then enable notifications. Optionally turn on **Start Shipshape when I log in** in Settings. Each Mac builds its own inventory.

Release builds are Developer ID signed and notarized by Apple, with tickets stapled to the disk image and the app. Each release on GitHub includes `SHA256SUMS.txt` with the disk image's checksum. Never disable Gatekeeper to install or distribute a build.

From 0.3.14, Shipshape updates itself with [Sparkle](https://sparkle-project.org). Once a day it reads `appcast.xml` from the latest GitHub release (**Check for Updates…** in the app menu and Settings checks right away). A newer version is shown with its release notes, and nothing is installed until you click **Install Update**. Sparkle then downloads the disk image, verifies its EdDSA signature against the public key in `Info.plist` and its Developer ID signature against the installed copy's, and quits, replaces and reopens Shipshape. The feed itself is signed too, so its notes and links can't be altered. **Check for updates automatically** in Settings turns off the daily check; updates are never installed without the click.

A fresh check runs every time the app opens, including at login, once the network is up (after 30 seconds it checks anyway). Checks also run daily at 9 a.m. America/Los_Angeles while the app is open, and catch up after waking. **Check now** runs one whenever you like; the dashboard footer and menu show the last check's time and how long ago it was ("10:36 AM (5 minutes ago)"). There is no background polling between checks. A first check takes a few minutes because NVD limits requests without an API key; NVD results are reused for 20 hours. **Quit** in the Dock (or the Command-Tab switcher) closes the dashboard and the Dock icon but keeps Shipshape checking from the menu bar; opening the dashboard brings the icon back. **Quit** in the menu bar panel, Command-Q, logging out and restarting stop monitoring.

The **Security** page starts with a summary card. Its status badge names the most urgent kind of finding: **Act now** (red) for malicious packages or known exploitation, **Fix soon** (orange) for security fixes or end of support, **Nothing urgent** (green) when only findings waiting for a fixed release or updates remain, and **All clear** (green) when there are none. Below it are how many items need attention and a bar of every inventory item by its most urgent finding, with each kind's count in the legend. The corner shows the share of items that need no action (no findings, or only findings waiting for a fixed release). Six tiles sort findings into malicious packages, known exploitation, security fixes, end of support, waiting for a fix and updates. A tile with findings takes its bar color (orange, gray or blue), and malicious packages and known exploitation are filled red. A tile lists only its findings, and **Needs attention**, the default list, holds the first four kinds. The menu bar panel shows the same kinds with their counts, and clicking one opens the Security page at that list.

**History** logs every recommendation: when it was first found and, once a check no longer reports it, when it was resolved and how. "Updated to 9.0.2" means the same software is now at another version; "Removed" means an older Homebrew copy was cleaned up; "Removed from this Mac" or "from the project" means the software is gone; "Project folder no longer checked" means its folder was taken out of Settings; and "No longer reported" means the software is unchanged but the advisory no longer matches. A finding that comes back, or is still reported after a version change, starts a new entry. Findings kept as unverified after a failed check stay open. History is stored with the latest result in Application Support, keeps the newest 10,000 entries (dropping the oldest resolved ones first), and exports as CSV. The first launch of a version with History starts it from the last saved result.

Notifications are deduplicated by installation, version, fix version, advisory identifiers and known-exploitation status. Malicious packages get their own alert title. A finding waiting for a fix alerts only once it's exploited (**Known exploitation, no fix yet**), and then once per installed version, so the advisories NVD adds each week don't repeat it. A bundled Sparkle or Electron gets an alert naming its app once the app's newer release has been out a week without being installed, which says only that the release may include a newer Sparkle or Electron. Failed source checks produce a separate alert and keep earlier findings visible as unverified.

**Excluded by design:** Google Chrome, whether installed directly or with Homebrew, and every app installed from the Mac App Store, including ones built on Electron. They update through Chrome's own updater and the App Store, and are skipped entirely: not listed, checked or counted as findings. Playwright's Chromium builds and the Chromium inside other Electron apps don't update with Chrome, so they're checked (see below).

**App signatures.** Inventory's **Signatures** list shows how each app is signed: **signed by team** (the developer's team ID), **signed by Apple**, **ad-hoc signed** (a signature that names no developer, as Xcode, `swiftc` and other build tools leave apps built on this Mac; linker-signed code counts as ad hoc) or **unsigned**, and whether it has the **Hardened Runtime**, which protects an app from code injection and unsigned libraries and which notarization has required since 2020. Apps that are ad-hoc signed, unsigned or without the Hardened Runtime come first and can be filtered, the Apps list notes them beside the version, and Coverage names them. They're never findings and don't affect the Security page, since apps built on your Mac and some Homebrew casks are ad-hoc signed by design. The signature is read with the Security framework (`SecStaticCodeCreateWithPath` and `SecCodeCopySigningInformation`) without running `codesign`, opening the app or checking its files against the signature, so all apps together take well under a second; Gatekeeper still assesses downloaded apps when they first open.

Versions are read by their first number, so an app that reports `Build 4215` compares as 4215. As a final check on every scan, an update is never offered when its version is the installed release written differently. Homebrew rebuilds such as 15.0.0 → 15.0.0_1 still count, and anything skipped is noted under Coverage.

CISA's Known Exploited Vulnerabilities catalog raises the priority of any finding whose CVE is listed, and the card gives the date CISA listed it. Homebrew's public metadata marks ordinary newer releases as updates, not security fixes. RustSec "unmaintained" notices are not reported as vulnerabilities.

**Advisory dates.** A card's explanation ends with when its advisory was first published, or the newest one's date when there are several, plus how long ago within 30 days; malicious-package reports say "Reported". Hovering an advisory ID shows its own date, and a CVE listed beside the GitHub advisory for the same issue says which one it matches and gives that advisory's date (the CVE itself may be older), so no date shows twice. Dates come from data each check already downloads: OSV's `published`, NVD's `published` (when NVD published the CVE, which can be days after the vendor's advisory), GitHub's `published_at` and CISA's `dateAdded`. Vendor pages without per-advisory dates (Node, PostgreSQL, OpenSSL) show none. Dates are for display only: they don't affect the order of findings, their urgency or alerts. NVD results cached by an earlier version show dates once the 20-hour cache refreshes.

**Links.** Each advisory ID links to its own page (the source's, NVD for CVEs, OSV otherwise); finding cards have no other web link. Copy and Show in Finder appear while the pointer is over a finding's location.

**Hiding a finding.** The **Hide** button on a card hides its finding, or every finding on a combined card, until something changes: the installed version, whether a fix can be installed, known exploitation or a malware report (`Hiding`). New advisories alone don't bring it back, so a Chromium NVD adds CVEs to each week stays hidden. A hidden finding leaves the counts, badge, tiles, menu bar and alerts, and is listed under **Hidden** at the end of the Security page, where its card's **Unhide** button puts it back. History still lists it as open.

**Cards.** Text in a finding, summary or Coverage card can be selected and copied (SwiftUI selects one piece of text at a time, such as the explanation or the version line). Each finding has a bug button (**Report a problem**) that opens a filled-in GitHub issue; a card combining several findings under one command also has one in its header, which reports the shared command and every finding in it.

**While a check runs.** A check reports its route as it goes (`CheckProgress`): each step's state and what it found, a line on this moment, and a line on why it takes the time it does or what leaves the Mac. The window shows all of it under its heading, and the list folds away; the menu bar panel shows the current step and the count. NVD's step tells the time left from the requests still to make. Steps that don't apply to this Mac leave the route. Scenario previews have checks off, so to see the steps, open the Dev copy with `SHIPSHAPE_STATE_DIR` and without `SHIPSHAPE_NO_CHECKS`.

**Packages a tool holds back.** An npx cache folder records the tool it was asked to run (`package.json`) and every package's dependency ranges (`package-lock.json`), and the card names the tool. A flagged package is held back when a range rules out its fixed version and the package with that range is the tool, or is pinned to one exact version all the way down from it; a looser range could resolve differently next time, so it isn't counted (`NpxCache`). When the tool's newest release on npm asks for the same, the finding waits for a fix with no command, because deleting the cache would only reinstall it. It alerts when a release asks for something else, and then offers the command again. Without npm's answer a waiting finding keeps waiting, and Coverage says so. Malicious packages aren't held: they're flagged for removal, whatever needs them.

NVD matching uses only explicit version ranges or exact versions on macOS-applicable configurations. Pre-release and unbounded "all versions" entries are ignored. NVD can lag vendor advisories, and Homebrew sometimes ships patches without changing a version, so NVD findings say so.

**npm's placeholders.** When npm takes a package down, or holds a name at risk of malicious use, it publishes an empty placeholder version such as `0.0.1-security`. OSV's malware report for the name covers every version, so the placeholder matches it, but it holds no code. A placeholder whose only advisories are malware reports is listed under Updates to remove, with the same uninstall command a malicious version gets, rather than as malware; other versions of the name still count as malicious.

**Python's branches.** Python's CVE records, and so NVD's, often give one range for every branch ("before 3.13.14"), though each branch gets the fix in a release of its own. So each CVE NVD lists for a Python is compared with the affected releases OSV works out from the fix commits. A release past all those listed in its branch already has the fix: it isn't a finding, and Coverage lists it under **Fixes already in older branches**. An earlier release takes its own branch's fix. If OSV lists no release of that branch, the CVE stands, and the only known fix is in a newer branch. Installing that branch leaves the old one in place, so a uv Python's card moves on as you do: `uv python install 3.13`, then `uv python upgrade 3.13` if it's behind the fix, then `uv python uninstall 3.12` once a fixed Python is there. A Homebrew Python on its formula's newest release has nothing to run, so it waits, as below.

**Playwright's browsers.** Playwright downloads its own browser builds and never updates them; each Playwright release names the builds it uses in its `browsers.json`. Every Playwright that runs `playwright install` leaves a file in the cache's `.links` folder naming where it's installed, and the next install deletes builds no linked Playwright uses. Shipshape reads the same links, plus any `playwright-core` it finds among global packages, the npx cache and project folders, to tell which Playwright uses each build (`Playwright`). Each build's version comes from its own app or, for Chromium's headless shell, the manifest it carries. A build nothing uses is listed under Updates with `cd ~/Library/Caches/ms-playwright && rm -rf chromium-1243 …`, which deletes it as Playwright would. It isn't checked for vulnerabilities, since nothing runs it, like an older Homebrew copy. A Chromium or Firefox build a Playwright uses is checked against NVD as Chrome or Firefox, which can list over a thousand CVEs for an old Chromium, so a card shows its twelve newest advisories until asked for the rest. Updating Playwright brings only the fixes its newest release ships, so Shipshape reads that release's `browsers.json` from GitHub. If it has none of the fixes, the finding waits for a fix, and a Chromium card points out that Playwright can run on Google Chrome meanwhile (`channel: 'chrome'`), since Chrome updates itself. Otherwise the card says how many fixes the update brings and offers the command: `pnpm add -D @playwright/test@latest && pnpm exec playwright install chromium` in the project (npm, pnpm, Yarn or Bun, from its lockfile), or deleting the npx install that uses the build.

**When an app's newest release has the fix.** A Sparkle or Electron inside an app is fixed only by a release of the app, so for each app with such a finding, Shipshape finds its newest release: from its electron-builder feed (`Contents/Resources/app-update.yml`, then the `latest-mac.yml` it names), its Sparkle feed or Homebrew's cask data, in that order. When that release is a zip, Shipshape reads the bundled framework's version from inside it without downloading it (`ReleasePeek`): a zip ends with a directory of its files, so four HTTP range requests read the size, the end, the directory and the framework's `Info.plist`, a few hundred kilobytes of a 150 MB update. A server that would send the whole file is cut off. Each release is read once and remembered. The card then says what the release has: **Fix available as of Nov 5 in Signal 8.34.0**, out of waiting with an alert that the fix is in it; **Some fixes**, with how many; or, when it has none, it keeps waiting as **43.8.7, not in Signal 8.34.0 yet**, naming the release it looked at, and alerts once a later one has the fix. An Electron release counts as having a fix by the rule the finding uses, an advisory published no more than a week after the release came out, and as complete only on a major that still gets fixes; a Sparkle by OSV's fixed version. Disk images and installer packages can't be read in parts, so for apps that ship only those, such as Discord or Mullvad VPN, the card can only say that a newer release is out. Claude, whose updater follows its own channel, isn't read.

**Apps built on Electron.** An Electron app carries its own Chromium, which changes only when the app ships a release on a newer Electron. Shipshape reads the Electron version from the app's `Electron Framework.framework` and lists it as Electron in the app, as it does a bundled Sparkle. Electron's own advisories come from OSV. Electron's public release list (`releases.electronjs.org`, which receives nothing about the Mac) gives each release's date and Chromium, and says which majors still get fixes: the newest three, with each major's support ending when the one three above it comes out. Electron copies Chrome's security fixes into supported releases, usually within days, without changing the Chromium version a release names, so NVD can't tell which Chrome vulnerabilities a release has fixed. Shipshape counts only those NVD published more than a week after the app's Electron release, which that release is very unlikely to have fixed; a few published just after it may be missed. The card names the Electron's Chromium and says whether its major still gets fixes, and the fix is the newest release of its major, or of the oldest supported major once its own has stopped. Only the app's developer can ship that, so the finding waits under **Waiting for a fix** unless a newer release of the app is known (from Homebrew's cask data or a Sparkle feed) and has been out a week; most Electron apps update from their own servers, so the card says Shipshape can't see a newer release and to check in the app. A Chrome vulnerability CISA lists as exploited moves the card to **Known exploitation** while it waits.

**No fix released yet.** Sometimes NVD lists no fixed version and the installed Homebrew copy is already Homebrew's newest release, so updating can't help. Those findings appear in their own group with no update command, and they don't count toward items needing attention or trigger alerts unless one is exploited. They show the fix version when an advisory's text names one ("before 1.22.3"). When Homebrew ships a newer release, the finding becomes an ordinary one with its command, and the alert says **Fix now available**. If Homebrew's data can't be loaded, the finding keeps waiting.

Vendor rules fail closed: a missing page or an unfamiliar format marks the check as failed instead of reporting software as safe. The one exception is a new OpenSSL release branch with no vulnerability page yet. It counts as having no published vulnerabilities, but only when OpenSSL's vulnerabilities index loads, links other branches and doesn't list that one.

To cover more software, add an entry to `native/Sources/Catalog.swift` with its bundle IDs, Homebrew formulae or casks, and one advisory source: an NVD CPE (`vendor:product`), an OSV package (`{major}` in a name follows the installed major version, as in Go's `/v5` module paths), or the project's GitHub repository advisories. Check that the source has data before adding it; the app reports nothing for a CPE or package it doesn't know, and a product whose versions don't match its package's versions needs its repository advisories instead. A Sparkle app that sets its update feed in code rather than in `SUFeedURL` can list its public appcast as `feed`.

**Coverage is partial.** Vulnerabilities in editor extensions (no public database covers them), CocoaPods, container images, unpinned MCP servers that npx hasn't cached, GitHub Actions pinned to branches or bare commits, software outside the catalog and arbitrary install paths aren't checked. A newer version alone is not a vulnerability. This is an update monitor, not a malware scanner or an assurance that a Mac is secure.

## Installing updates

Each finding lists the ways to install its fix, best first, with the others under **Other ways to update**. The app checks how the software was installed and what this Mac has (Homebrew, mise, npm, pnpm, Yarn, Bun, corepack, uv, Poetry, Cargo, Bundler, Go, nvm, Volta, fnm), and uses Homebrew's data on whether each app updates itself. Options come in four kinds:

- **Terminal command**, matched to the install method: `brew upgrade curl`, `cd ~/Projects/app && npm install next@16.4.1`, `npm audit fix` for transitive dependencies, `uv lock --upgrade-package`, `mise upgrade node`, `claude update`, `opencode upgrade` or the owning interpreter's `pip`. **Copy**, to the right of the command, puts it on the clipboard to paste into any terminal.
- **Website**: the vendor's download page, nodejs.org, python.org or go.dev. Only https pages are offered.
- **App**: opens an app that updates itself so its updater can install the release.
- **File**: opens requirements.txt, package.json or an MCP configuration where a pin has to change, in your text editor (never the app the file type would launch), and only when it's a plain, non-executable text file inside a chosen project folder or one of the MCP settings files Shipshape reads.

For a directly downloaded app, one that updates itself leads with opening it, then a Homebrew command if Homebrew is installed, then the download page. An app without a self-updater leads with Homebrew or the download page. Homebrew apps that update themselves get `--greedy` so Homebrew includes them. When a project's package manager isn't installed, the command first installs it (`corepack enable pnpm`, `npm install -g yarn`, `brew install uv`), or the first option is its install page. Older Homebrew copies get `brew upgrade X && brew cleanup X`, because Homebrew deletes them only once its newest build is installed; removing just that copy from Homebrew's Cellar is offered as an alternative. Pinned formulae are unpinned before upgrading, and a pinned formula's old copy is removed without upgrading. Homebrew rebuilds, such as 26.12.1 → 26.12.1_1, appear as updates. Apple updates open Software Update. Installers downloaded from nodejs.org or python.org are checked with Apple's notarization assessment before `sudo installer` runs. 

**Commands only for what your account can change.** Before offering a command, Shipshape checks that the signed-in account can write where it acts: the project folder, its lockfile, `node_modules` (including npm's `@scope` folders) and `.venv`, Homebrew's Cellar and Caskroom, the global package folder or Python `site-packages`, the npx cache and MCP settings files. If not, the finding stays listed (the vulnerable code is still on the Mac) with a lock notice in place of the command, naming the folder and its owner. Another account's projects say to make the fix from that account. Homebrew installed by another account says only that account can upgrade it, also noted under Coverage. A root-owned folder in a project is usually left by an install run with `sudo`; change its owner back to your account. Shipshape never suggests running package managers with `sudo`. Adding a project folder that belongs to another account, or that includes system or Homebrew folders, shows a warning in Settings. The welcome screen and Settings suggest folders Claude Code and Codex have worked in (`ProjectSuggestions`), read from the project paths in `~/.claude.json` and `~/.codex/config.toml`: those with a lockfile within two levels, as their parent folder when two or more share one, never the home folder or above it. Nothing is added until you click, and scenario previews show no suggestions.

Project scans skip app bundles, Homebrew's own folders (`/opt/homebrew`), `/usr`, `/System`, `/Library`, `~/Library` and Go's module cache, so a project folder set high up, even `/`, doesn't pick up package-manager internals as projects. A folder chosen inside one of those is still checked.

Findings whose recommended command is the same, or differs only in what it acts on, appear as one card with one combined command (`brew upgrade a b c`, `rm -rf dir1 dir2`, `npm install next@16.4.1 ai@5.0.52`), followed by each finding's version, reason, location, advisories and any alternatives of its own. All older Homebrew copies share one card, and so do a project's indirect dependencies under its `npm audit fix`. **All commands…** on the Security page lists every recommended Terminal command in the list showing, combined the same way, with each project's commands kept together, to review and copy one at a time or all at once. Commands that can't take several targets, such as `cargo update --precise`, stay one per line. On the developer's Mac, 187 security findings became 44 cards and 28 commands, and 52 updates became 4 cards and 3 commands.

Package names and versions are checked against each ecosystem's naming rules and shell-quoted before they appear in a command, and nothing is ever run by the app. Review a command before running it; dependency updates can change behavior.

## Hardening

- **Untrusted project files.** Project scans don't follow links, read only regular files up to 64 MB, and stop after 60 seconds, reporting what was left. Parsers are linear in file size; a `requirements.txt` crafted to slow a regular expression parses 20,000 lines in milliseconds.
- **No hidden characters in commands.** A path or name containing control, formatting (including bidi) or line-separator characters gets no Terminal command. Pasted into a shell, such characters could erase the line or run something else. The finding shows where they are instead.
- **Opening files and apps.** Files open only in your text editor, and only when they are plain, non-executable text files inside a chosen project folder or one of the known MCP settings files. A repo can't turn "Open package.json" into running a script. Apps open only from Applications folders.
- **No Homebrew code runs.** The Homebrew inventory is read from `Cellar`, `Caskroom`, `opt` and `var/homebrew/pinned` directly. Other programs (`node --version` and similar, `softwareupdate`) run only if this account or root owns them and no one else can change them, with a minimal environment.
- **Bounded downloads.** Every source has a size limit, enforced while downloading: a larger declared size is refused before the body arrives, and transfers stop as soon as they pass the limit.
- **Signed updates only.** Shipshape installs an update only when the release's disk image carries both an EdDSA signature from the update key and the same Developer ID, and the feed describing it is signed with the same key. A tampered feed is refused with an error. Sparkle's XPC services, which only sandboxed apps use, are removed from the bundle.
- **Quoted names and no stray keys.** Package names are quoted in every command, even after validation. An MCP server's arguments are recorded only when every option before the package is known, so an option's value, such as an API key, is never mistaken for a package name.

## Data and privacy

State lives in `~/Library/Application Support/Shipshape/state.json` (folder 0700, file 0600). It contains local paths, project folders, package names, versions, results and notification fingerprints. There is no analytics, account, remote inventory or AI service. App signatures are read on this Mac and never sent anywhere.

Project paths in `~/.claude.json` and `~/.codex/config.toml` are read only to suggest project folders, and never leave the Mac. When Xcode or the Command Line Tools are installed, python.org's release cycle (`peps.python.org/api/release-cycle.json`) is downloaded; nothing about the Mac is sent. Package names and versions are sent to OSV, along with the IDs of CVEs NVD lists for a Python; product names and versions go to NVD, and release and advisory lookups to Homebrew, GitHub, Node, PostgreSQL and OpenSSL. npm receives the name of a tool run with npx, only when that tool holds back a flagged package. When a browser build a Playwright on this Mac uses has NVD findings, npm and GitHub receive Playwright's name and the version of its newest release, to read which browsers that release ships. When an app built on Electron is installed, Electron's public release list is downloaded; nothing about the Mac is sent. For an app with a vulnerable Sparkle or Electron inside, its electron-builder feed and a few hundred kilobytes of its newest update zip are fetched from its developer, as its own updater would. Self-updating apps' Sparkle feeds are fetched from each app's developer, the same request the app makes when it checks for updates. Shipshape's own update check fetches its feed and, when you install, the disk image from GitHub; the request names Shipshape's and Sparkle's versions, and Sparkle's system profiling is off. **Private package names in your lockfiles are included in OSV queries.** MCP settings are read for each server's command and arguments only; environment variables, headers and keys are never kept. Lockfiles are read as text and nothing in a project is run. Exported reports contain local paths and package names, so review them before sharing.

To uninstall, turn off Start at login, quit the app and move it to Trash. Remove the Application Support folder separately if you no longer need saved results.

## Development

Requires Xcode or a matching Swift compiler and macOS SDK. The one third-party package is Sparkle, for Shipshape's own updates: `native/sparkle.sh` downloads its pinned release into `native/work`, checks the SHA-256, and the build embeds and signs it.

```sh
bash native/test.sh
SIGN_IDENTITY="Developer ID Application: YOUR NAME (TEAMID)" bash native/build.sh
SIGN_IDENTITY="Developer ID Application: YOUR NAME (TEAMID)" bash native/package.sh
bash native/notarize.sh security-monitor-notary
bash native/appcast.sh
```

`bash native/scenario.sh NAME` opens a copy of the app on made-up findings (`native/Tests/Scenarios.swift`: first-run, all-clear, waiting-only, typical, malware, exploited, everything, crowded and check-issues), with `SHIPSHAPE_STATE_DIR` set to a fresh copy of the scenario and `SHIPSHAPE_NO_CHECKS=1`, which turns off the launch, daily and Check now checks when a state folder is set. The copy is named Shipshape Dev (its `CFBundleName`, shown in the menu bar, window and sidebar) with an orange icon (`make-icon.swift ROOT dev`; built with `ShipMark.swift`, the ship the app draws as its logo, so the icon and the app share one drawing), and `SHIPSHAPE_SCENARIOS` points it at the generated scenarios, which its Scenarios menu and menu bar panel switch between. To try a development build without touching the installed app's saved results, launch it with `SHIPSHAPE_STATE_DIR` set to another folder, for example `open -n --env SHIPSHAPE_STATE_DIR=/tmp/shipshape-state dist/Shipshape.app`. Without it, a development build uses and changes the installed app's data. The name and version come from `native/Resources/Info.plist`; the build, packaging and notarization scripts read them from there, and `appName` in `Feeds.swift` is the name shown in the app. The notary keychain profile keeps its original name. Without `SIGN_IDENTITY`, the build uses an ad-hoc signature for local development only. Tests cover version ordering, vendor range rules, each lockfile format, MCP command parsing, OSV alias handling and fix selection, NVD range and platform evaluation, command quoting and routing, app signature classification, advisory dates and links, failed-check retention, notification fingerprints and Pacific-time scheduling.

For a command-line scan with the same engine (pass an output file and any project folders):

```sh
xcrun swiftc -swift-version 5 -O -parse-as-library native/Sources/{Models,Catalog,Lockfiles,Inventory,Advisories,Commands,Feeds}.swift native/Tests/Check.swift -o native/work/check
native/work/check native/work/live-scan.json ~/Projects
```

Every rebuilt DMG needs its own notarization before sharing. `native/notarize.sh` submits the DMG with a saved notarytool keychain profile, waits for **Accepted**, staples the DMG and app, verifies Gatekeeper acceptance and rewrites the checksum. Run `native/setup-notarization.command` once in Terminal to save the `security-monitor-notary` profile. Never put Apple passwords in source files or shell history.

Updates are signed with an EdDSA key. Run `native/setup-update-key.command` once in Terminal: it creates the key in your login Keychain (account `shipshape`), or reuses it, puts the public half in `Info.plist` as `SUPublicEDKey`, and offers to write a backup to put in your password manager. **Keep that backup.** Installed copies trust only this key, so losing it means everyone has to download the next release by hand. A signed release build refuses to start without `SUPublicEDKey`. After notarizing, `native/appcast.sh` writes `dist/appcast.xml` for the disk image, with its signature and the version's dated `CHANGELOG.md` section as release notes, then signs the feed. Attach `appcast.xml` to the GitHub release with the disk image and `SHA256SUMS.txt`; installed copies read it from the latest release's download link. Development builds launched with `SHIPSHAPE_STATE_DIR` don't check for updates unless `SHIPSHAPE_CHECK_UPDATES=1` is also set.
